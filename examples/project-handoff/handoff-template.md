# Task handoff

## Goal and accepted constraints

What result does the user want? Which scope, product choices, and constraints
have they already confirmed? Reference the existing brief when available.

## Current state and evidence

- Working location and branch/revision, if relevant:
- Intentional uncommitted work to preserve:
- Applied changes, each with a file or external result reference:
- Checks actually run: command/action, outcome, revision or date:
- Checks not run or evidence no longer current:

## Decisions and unknowns

Separate user-confirmed decisions, AI proposals, and open questions. State
which missing answer would change the next action and who can decide it.
Keep unresolved alternatives visible without restating the whole design.

## Next action and verification

Name the smallest useful next action, the files or systems it concerns, and
the observable result that would support or reject it. Link the relevant
instructions. State the stop condition if access, evidence, or authorization
is missing.

## Authority and data boundary

Record the scope of existing user authorization. A handoff is not permission
to publish, message someone, migrate configuration, or expand the task.
Keep credentials out of this file; refer to the authorized mechanism by name.
Keep this record in the project with its existing access permissions. Check
the public boundary before committing a real handoff to a public repository.
